# 2.1 大语言模型工作原理

## 2.1.1 注意力机制和上下文(自己看笔记)

1. **Query、Key、Value**：每个 Token 被转换为三个向量
2. **注意力分数计算**：Query 与所有 Key 计算相似度
3. **加权求和**：根据注意力分数对 Value 加权求和
4. **输出表示**：得到融合了上下文信息的 Token 表示

## 2.1.2 计算复杂度

准自注意力的计算复杂度是 $O(n^2)$，其中 $n$ 是序列长度。这意味着：

- 序列长度翻倍，计算量增加 4 倍
- 这是限制上下文窗口大小的主要技术瓶颈

| **技术**                                       | **原理**                                                     | **代表模型**                |
| ---------------------------------------------- | ------------------------------------------------------------ | --------------------------- |
| **稀疏注意力（Sparse Attention）**             | 只计算部分位置之间的注意力，减少需要计算的注意力连接         | Longformer、BigBird         |
| **线性注意力（Linear Attention）**             | 对自注意力进行近似，将注意力计算复杂度从二次级别降低到近似线性级别 | Linear Transformer          |
| **滑动窗口注意力（Sliding Window Attention）** | 限制每个位置只关注其附近的局部窗口，避免计算完整的全局注意力 | Mistral                     |
| **分组查询注意力（GQA）**                      | 多个 Query 头共享较少数量的 Key-Value 头，从而减少 KV Cache 和推理时的内存占用 | LLaMA 2 70B、许多现代大模型 |

## 2.1.3 预训练和涌现能力

语言模型通过在海量文本上预训练，学习语言的统计规律和世界知识。随着模型规模、训练数据、后训练方法和工具接口共同演进，模型会逐步表现出更强的 **涌现能力**（Emergent Abilities）：

- 少样本学习：通过几个示例就能理解新任务
- 逻辑推理：执行多步推理
- 代码生成：根据自然语言描述生成代码
- 工具使用：理解和调用外部工具

# 2.2 上下文窗口的本质

## 2.2.1 什么是上下文窗口

上下文窗口是LLM一次能够处理的最大token序列长度
它包括输入的提示词,对话历史,检索到的文档等信息,以及模型的输出

类比为模型的工作记忆:

- 有固定的容量上限
- 超出容量的部分无法处理
- 窗口内所有信息可见且相互影响

## 2.2.2 输入和输出的关系

上下文窗口容量=输入*T**o**k**e**n*数+输出*T**o**k**e**n*数

## 2.2.3 上下文窗口的技术实现

- 位置编码:现在多采用**RoPE**（旋转位置编码）和 **ALiBi**（注意力线性偏置）
- KV缓存
- 注意力计算

## 2.2.4 长上下文的挑战

- 中断迷失:对开头和结尾的信息更敏感
- 注意力稀释:噪声,冲突证据,位置偏置的暴露面更大
- 成本和延迟
- 质量和长度的权衡

## 2.2.5 有效上下文的长度

声称上下文长度:宣称支持的最大程度
有效上下文长度:真正能够有效利用的长度

评估有效上下文长度:大海捞针测试:将一条关键信息放置在上下文不同位置,看测试模型能否正确检索

# 2.3 Token与上下文限制

## 2.3.1 什么是token

token是LLM处理文本的基本单位
它可以是:

- 一个完成的单词
- 单词的一部分
- 单个字符或者标点符号
- 特殊符号

## 2.3.2 分词算法

主流的算法包括:

- **
  BPE（Byte Pair Encoding）**: OpenAI 的 GPT 系列采用，从单字符开始迭代合并最频繁出现的字符对，直到达到预设的词表大小
- **WordPiece**: Google 的 BERT 采用，与 BPE 类似但使用不同的合并策略
- **SentencePiece**: 处理多语言文本的通用方案，不依赖于预先的空格分词，特别适合中文、日文等语言

2.3.3 Token计数的重要性

1. 容量规划:防止请求过长被截断
2. 成本估算
3. 性能优化

### 2.3.4 Token计数实践

Tokenizer: 采用官方的分词器

- OpenAI：tiktoken 库
- Anthropic：Claude 分词器
- Google：Gemini tokenizer

## 2.3.5 上下文限制的管理策略

### 预算分配:

为不同组成部分分配token预算:例如系统提示词,检索内容等等

### 内容筛选

只包含当前任务真正相关的信息:
精确检索而非全量加载;移除冗余和重复内容;过滤噪声信息

### 格式优化

简洁的表达;避免不必要的格式修饰;结构化而非散文化表述

### 动态调整

简单任务使用更小的上下文;复杂任务拓展必要信息;实时监控token使用情况

## 2.3.6 token与成本

输入,输出,缓存读,缓存创建对应的token计费规则不同

成本优化策略:

- 压缩输出
- 控制max_tokens控制最大输出长度
- 简单利用prompt caching机制复用公共内容
- 简单任务使用小模型.复杂的用大模型
- 批量请求可能有折扣

# 2.5 SSM vs Transformer 在上下文工程中的对比

## 2.5.1 引言: 架构之战如何影响上下文策略



- **自注意力复杂度**：Transformer 为 O(n²)，SSM 为 O(n)
- **上下文长度成本**：长上下文下，Transformer 费用陡增，SSM 线性增长
- **信息流向**：Transformer 全局互注，SSM 线性扫描
- **检索策略**：需要不同的优化方向

## 2.5.2 Transformer自注意力机制和上下文成本

Transformer 的核心是自注意力（Self-Attention）机制。对于长度为 n 的上下文序列，注意力的计算方式为：

```
Attention(Q, K, V) = softmax(Q·K^T / √d_k)·V
```

Q,K,V来自同一个source即为input(这里有关于transformer的理解,自己去看笔记)

成本特征:

- 时间复杂度:O(n ^2),n为上下文长度
- 空间复杂度:朴素训练实现会产生 O(n²) 注意力中间状态；现代推理通常通过内核优化避免长期保存完整注意力矩阵，但 KV Cache 仍随上下文长度线性增长
- 每个token的成本随上下文线性增长:第 i 个 Token 需要计算与所有(i-1)个前序 Token 的注意力

### Attention中的上下文丢失问题

注意力分散的问题:导致Transformer理论上能看到所有内容,但是在实际应用中,会对关键信息注意力不足.存在"Lost in the Middle"现象
